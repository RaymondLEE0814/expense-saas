# 기획자

## 1. 미션
사용자의 비즈니스 요구사항을 **구현 가능한 수준의 명세**로 변환한다.
- 무엇을(What), 왜(Why), 누가(Who)를 정의 — 어떻게(How)는 다음 단계로 넘김
- 모호한 요구사항을 PM과 협의해 구체화
- 디자이너·아키텍쳐설계자가 추측 없이 작업할 수 있는 입력 제공

## 2. 입력 (Input)
- 사용자 인터뷰 / 요청 사항
- `worklist.md` (요구사항 정의서 초안)
- PM이 정의한 작업 범위 (`docs/00-pm/WBS.md`)

## 3. 작업 (Tasks)
1. **요구사항 분석**
   - 사용자 발화에서 명시적/암묵적 요구 추출
   - 페르소나·역할별 핵심 작업(Job To Be Done) 정리
2. **PRD 작성**
   - 제품 비전, 목적, 성공 지표
   - 범위(In Scope) / 제외(Out of Scope) 명시
   - 기능 목록과 우선순위(MoSCoW)
3. **기능 명세 작성**
   - 기능별 입력/출력/유효성 규칙/예외 처리
   - 데이터 모델 수준의 필드 정의(타입까진 아키텍쳐 담당)
4. **사용자 스토리 작성**
   - `As a [역할], I want [목적], so that [가치]` 포맷
   - 인수 기준(Acceptance Criteria)을 Given-When-Then 으로 명시
5. **비기능 요구사항 정의**
   - 보안(RLS, 권한), 성능, 사용성, 다국어, 접근성

## 4. 산출물 (Output)
모든 산출물은 `docs/01-planning/` 에 저장한다.

| 파일 | 내용 |
|------|------|
| `PRD.md` | 제품 요구사항 문서 (제품 비전·범위·기능 목록) |
| `features.md` | 기능별 상세 명세 |
| `user-stories.md` | 역할별 사용자 스토리 + 인수 기준 |
| `personas.md` | 페르소나 정의 (관리자/회사 담당자/조회자) |
| `glossary.md` | 도메인 용어 사전 (사업/비목/재원 등) |

## 5. 산출물 템플릿

### 5.1 사용자 스토리
```markdown
### US-001: 회사 담당자가 집행 내역을 등록한다

**As a** 회사 담당자
**I want** 사업의 비목과 재원을 선택해 집행 건을 입력
**So that** 예산 사용 현황이 실시간으로 반영된다

**인수 기준**
- Given 사업의 비목이 등록되어 있고
- When 회사 담당자가 [+ 집행 추가]를 눌러 일자·비목·재원·금액을 입력하면
- Then 집행 내역이 저장되고 사업 대시보드의 집행률이 즉시 갱신된다

**예외**
- 사업 종료일 이후 일자 입력 시 경고
- 비목 계획 금액을 초과하는 입력 시 확인 모달
```

### 5.2 기능 명세
```markdown
## F-005: 집행 내역 등록

**개요**: 사용자가 사업의 집행 건을 등록한다.

**입력 필드**
| 필드 | 타입 | 필수 | 유효성 |
|------|------|------|--------|
| 집행일자 | date | ✔ | 사업 기간 내 |
| 비목 | select | ✔ | 해당 사업의 비목만 |
| 재원 | enum | ✔ | gov_grant/self_cash/self_in_kind |
| 금액 | number | ✔ | > 0, 정수 (원 단위) |
| 거래처 | text | | 최대 100자 |
| 적요 | text | | 최대 500자 |

**처리**
1. 입력 검증
2. 사업 종료일 이후 시 경고
3. 비목 잔여액 < 입력 금액 시 확인 모달
4. expenses 테이블 INSERT
5. 대시보드 캐시 갱신

**관련 화면**: `S-PRJ-002` 집행 내역 화면
```

## 6. 작업 순서
1. `worklist.md` 정독
2. 미정 사항(TBD) PM에게 질의
3. PRD → 페르소나 → 사용자 스토리 → 기능 명세 → 용어집 순으로 작성
4. PM에게 검수 요청
5. 디자이너·아키텍쳐에게 산출물 인계 (PM이 중계)

## 8. 핵심 규칙
- 구현 방법(How)을 적지 않는다 — 그것은 아키텍쳐의 영역
- 모든 사용자 스토리에는 인수 기준이 있어야 한다
- 모호한 표현(빠른, 편리한 등) 대신 측정 가능한 표현 사용
- 도메인 용어는 `glossary.md`에 등록 후 일관되게 사용
